## §17.19 短期路线学习(2026-07-18) ✅ 已构建

`MoveTask` 在同一维度、同一 8 格起点区域到同一 8 格目标区域耗尽安全路径与中继绕行后，向 `NavigationMemory` 写入一条 **30 秒、仅内存** 的路线失败记录。重复移动会立即以 `move_no_safe_route: recent_route_failure` 返回给既有失败恢复逻辑，不再重新执行同一套 A* 与中继搜索；起点/终点区域改变、30 秒到期或重新成功拿到路径时都会解除。它不会进入长期知识库或模型 prompt，也不会把可变的门、方块、玩家位置误判为永久危险地带。新增 `NavigationMemoryTest` 覆盖区域匹配、到期与成功清除。

补充逃跑链路：`EvadeTask` 现在不会只凭落点可站就开跑，而是在远距离撤离点与附近安全通道上各验证一次 A* 成功；两者都不可达才返回 `no_valid_escape_route`。这针对历史日志中地下岩壁另一侧“可站但不可达”点导致的连续逃跑空转。

部署：已替换 PrismLauncher 的 `1.21.3-DeepSeek` 与 `1.21.3(1)` 两个实例中 `mods/aibot-0.0.1.jar`。构建产物与两份已部署 jar 的 SHA-256 均为 `e1375ca92a6ae8704b8dc9ab8991ce966d1bc4b008eff7af437f99a876da8eec`；重启客户端后加载。

口播再收敛：TTS 出口额外清理 `好的！`/`收到！` 等变体，以及不改语义的 `我会先`、`我会去`、`我会继续`、`我会马上`、`我会试试` 开头，变成更直接的玩家口吻；新增回归断言确保这只是展示层处理，模型仍固定为 `step-3.7-flash`。

行为恢复修复：危险层的“连续战斗卡死后改为撤离”不再读取会被大脑消费的一次性 `pendingFailure`，而是读取稳定保存的 `lastFailure`。因此失败提示注入给 Step 后，生存层仍能保留连续 `stuck:combat` 的事实并切换策略，避免继续原样派发不可达战斗。

出生安全修复：`safeSpawnPosition` 不再把寻路用的“向下 128 格找可走点”用于出生修正。现在依次只查请求高度附近、同列地表、世界出生点附近；日志额外记录 `strategy`。这避免高处或暂未稳定的坐标被修正到深层洞穴/世界底部，从根源减少出生即死亡、异常跑尸和原地路径空转。

验证：`./gradlew test` 与 `./gradlew build` 均通过。尝试 `bash scripts/prod_test.sh nav_unreachable 180` 时，生产测试基座因本机缺少 `run-prod/fabric-server-launch.jar` 在启动前退出，未将其记为场景通过；需要恢复正式服务端启动器后再跑该场景。

## 二、本次会话暴露的 BUG

### 🔬 深度复审新修(2026-07-11,Opus 4.8 逐文件精读,前一批"✅ 已修"实为假象)

上一批模型把下列缺陷标成"✅ 编译通过/已部署"就交差,但**没有实测**,实际全是坏的。逐一实锤 + 修复 + 编译验证 + 单测:

| # | Bug | 根因(实锤) | 修法 |
|---|-----|-----------|------|
| 1 | **对话日志功能整个是死的** | `ConversationLogger.INSTANCE.start()` 全项目从未被调用(`AIBotMod` 只调了 `BotLogWriter.start`)→ `enabled` 永远 false → `all.log`/`all.jsonl` 一字不写。用户明确要求"必须写好日志" | `AIBotMod.onInitialize` 加 `ConversationLogger.INSTANCE.start(config)`;SERVER_STOPPING 加 `shutdown()` |
| 2 | **一旦启用日志,每条消息必崩(致命)** | `onUserMessage` 的 `summary("[%s] USER %s: %s\n", sender, text)` —— **3 个 `%s` 只喂 2 个参**。`String.format` 在 try 外抛 `MissingFormatArgumentException` → 冒泡穿 `handleMessage` → `submit()` 到不了 → **机器人对每条消息哑火**。定义好的 `TS` 时间戳格式器从没被用,正是漏掉那个参 | 补 `now()` 时间戳做第一个参;`summary()` 用 try/catch 兜底格式异常绝不外泄;所有 summary 行统一加时间戳(单测复现旧 CRASH + 验证新版不崩) |
| 3 | **finish 工具检测是死代码** | `ChatMessage.toolResult()` 把 `name` 恒设 null,但 `onResponse` 用 `"finish".equals(result.name())` 判断 → 永远 false。且 finish 与其它工具同批(`finish_reason=tool_calls`)时,`markTurnFinished` 把 busy 置 false 后 `onResponse` 仍走 `scheduleContinuation`(因 !busy 空转)→ **在途排队的用户消息被 stranded**,过后错误接续("很久前的旧消息莫名重现") | 加 `toolResult(id,content,name)` 重载并在 dispatcher 传 `call.name()`;`serializeMessages` 对 tool-role **不发 name**(防 StepFun 400);finishCalled 时就地 `drainPending` 并 return,不再 scheduleContinuation |
| 4 | **reasoning_content 从半句腰斩** | `substring(len-200)` 盲取末尾 200 字,回答从半个词/半句开始,读着是残句 | 新增 `conclusionTail()`:截末尾后从第一个句末标点之后起头,保证完整句(单测验证起头干净) |
| 5 | **plain text / 思考正文被自动 TTS**(用户反复投诉"没调 TTS 也把所有文本念出来") | 模型正文以 role `"bot"` 下发 → voice controller 见 role=="bot" 就念。系统提示词规则 6(说自动念)与规则 8(说静音)**自相矛盾** | 新增 `sendPanelDisplay()` 发 role `"bot_text"`:面板照显(绿气泡)但 voice controller 不念、OBS 气泡不更新;plain text 走它。观众音频**只经 speak/finish**。提示词规则 6/8 改为一致口径 |
| 6 | **日志 writer null 时 summary NPE** | `jsonl()` 有 null-writer 防护,`summary()` 没有(磁盘不可写即 NPE) | `summary()` 加 `if (w == null) return` |

**为什么这些能蒙混过关**:全是"编译通过 ≠ 能跑"的缺陷。format 参数不匹配、name 恒 null、start 没调——编译器都不管,只有实跑或单测才暴露。教训见 KB「No claim without verification」。

| **reasoning_content 全文泄露** | parseResponse 把整几百字 reasoning 当 content → TTS 全念 | 改为仅 `finish_reason=stop && content==空` 时取末尾≤200字符,tool_calls 时不进 content |
| **auto_continue 无限循环**(导致"Bob 停不下来/用户消息被忽略") | prompt 注入式`auto_continue_no_finish` 把工具结果重新注入 + 无脑 submit,5 次兜底不够 fast 阻止循环 | 整个机制禁用,改为 log 标记 + 清零 uncommittedTools |
| **speak/finish 工具不在系统提示词显眼位置** | 规则 12c 埋在末尾,模型权重低"不知道有 finish" | 系统提示词顶部独立段落强调"speak + finish 是你最重要的两个工具",并在"每完成一步工具链后必须 finish" |
| **未 finish 自动结束导致 turn 卡死** | 模型做完工具直接 stop 不 finish → busy 释放但玩家没被告知原因 | completion 分支检测到 uncommittedTools>0 且 finish_reason!=tool_calls → history 末尾追加醒目的 system 提示:"你忘了 finish,下轮请先 finish 解锁玩家" |
